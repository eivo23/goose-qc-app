# אפיון מערכת לבקרת טעויות ליקוט – מוצרי אווז

מסמך אפיון לגרסת MVP. גרסה 1.0 · 24/07/2026

מטרת המערכת: להחליף את קבוצת הוואטסאפ, לשמור כל תמונה, לזהות אוטומטית את שם הלקוח ואת המוצר, להשוות בין המוצר שהוזמן (מדבקה כחולה) לבין המוצר שנמצא בפועל (תווית היצרן על הקרטון), ולהתריע מיד כאשר יש אי־התאמה או חוסר ודאות. פשוט מאוד למלקט, חזק ומבוקר למנהל.

---

## 1. ניתוח שתי התמונות המצורפות

בכל קרטון יש שתי תוויות שהמערכת צריכה לקרוא ולהשוות:

- **תווית היצרן (הלבנה/הכחולה־כהה של Palmi-Top)** – מודפסת מראש על ידי היצרן ההונגרי, כתובה בעברית + צרפתית + הונגרית. זה **המוצר שנמצא בפועל בקרטון**.
- **המדבקה הכחולה (הבהירה)** – מודפסת מתוך ההזמנה (דרך "קנקון מוצרים" / "איב רשתות"). כוללת את **שם הלקוח** ואת **המוצר שהוזמן**, מספר חבילה (למשל 1/3), ומזהה ליקוט. זה **המוצר שהלקוח הזמין**.

### מונחון תרגום שחולץ מהתוויות (הונגרית → עברית)

זהו לב היכולת לעבוד בלי קטלוג. תווית היצרן כתובה בהונגרית, ומכאן נגזר:

| הונגרית (יצרן) | צרפתית (יצרן) | עברית (יצרן) | חלק |
|---|---|---|---|
| LIBAMÁJ | FOIE GRAS D'OIE | כבד אווז | כבד |
| LIBACOMB (comb = ירך/שוק) | CUISSE D'OIE | שוק אווז | שוק |
| LIBA SZÁRNYTŐ (szárny = כנף) | AILES D'OIE | כנפיים אווז | כנף |

הערה חשובה: המילה ההונגרית **comb** פירושה ירך/שוק (ולא "קומב" כלשהו), ולכן `LIBACOMB` = שוק אווז. `SZÁRNYTŐ` = בסיס כנף = כנף. `MÁJ` = כבד. המערכת חייבת להכיר את המילון הזה כדי לנרמל נכון.

### תמונה 1 – מלאי מעורב, מסומן בירוק ➜ **טעות ליקוט (חריגה)**

ערימה של ארבעה קרטונים. שני העליונים תקינים, שני התחתונים מסומנים בעיגול ירוק:

- **קרטון עליון** – יצרן: `כבד אווז קפוא / FOIE GRAS / LIBAMÁJ`. מדבקה כחולה: לקוח **מסעדת תיירות המפרץ (2011)**, הוזמן **כבד אווז 700/900**. ➜ כבד מול כבד = **תקין**.
- **קרטון שני** – יצרן: `שוק אווז קפוא / CUISSE / LIBACOMB`. מדבקה כחולה: לקוח **קיבוץ אילות (כפות תמרים)**, הוזמן **שוק אווז ואקום**. ➜ שוק מול שוק = **תקין**.
- **שני הקרטונים המסומנים בירוק** – יצרן: `שוק אווז קפוא / LIBACOMB` (שוק). מדבקה כחולה: לקוח **קיבוץ אילות**, אך המוצר **שהוזמן אינו שוק אווז** (על פי הדוגמה שלך: כבד אווז קפוא). ➜ **הוזמן כבד אווז, נמצא בקרטון שוק אווז = אי־התאמה, חריגה, התראה מיידית.**

הנרמול שהמערכת מפיקה כאן:

```
הוזמן  (מדבקה כחולה): { לקוח: קיבוץ אילות, בעל_חיים: אווז, חלק: כבד,  מצב: קפוא }
נמצא   (תווית קרטון): {                בעל_חיים: אווז, חלק: שוק,  מצב: קפוא }
תוצאה: חלק שונה (כבד ≠ שוק) → אי־התאמה → חריגה → Push
```

### תמונה 2 – שלושה קרטוני כנפיים ➜ **בדיקה תקינה**

שלושה קרטונים זהים:

- יצרן: `כנפיים אווז קפוא / AILES / LIBA SZÁRNYTŐ` (כנף). מדבקה כחולה: לקוח **מיטטוגו בע"מ** (דרך "קנקון מוצרים"), הוזמן **כנפיים אווז**, חבילות 1/3, 2/3, 3/3.
- ➜ כנף מול כנף = **תקין**. רצף חבילות שלם (1/3, 2/3, 3/3) → אין חריגת רצף. נשמר במסך "כל הבדיקות" ללא התראה.

```
הוזמן  (מדבקה כחולה): { לקוח: מיטטוגו, בעל_חיים: אווז, חלק: כנף, מצב: קפוא }
נמצא   (תווית קרטון): {              בעל_חיים: אווז, חלק: כנף, מצב: קפוא }
תוצאה: זהה → התאמה → תקין
```

### הסתייגות שקופה לגבי ה־OCR

התוויות הגדולות של היצרן (כבד/שוק/כנפיים + ההונגרית) קריאות בביטחון גבוה. הטקסט הקטן על המדבקה הכחולה בצילומי הוואטסאפ דחוס ולעיתים מטושטש – ולכן דווקא במקרה כזה **המערכת תפעל בגישה שמרנית**: אם קריאת המוצר שהוזמן אינה ודאית, הבדיקה לא תסומן "תקין" אלא תעבור לחריגות תחת "לא ניתן לזהות בוודאות את המוצר". זיהוי הטעות בתמונה 1 והתקינות בתמונה 2 תואמים את מה שתיארת.

## 2. עקרון הליבה – השוואה ללא קטלוג מוגדר מראש

המערכת **לא** מסתמכת על רשימת עשרה מוצרים, מק"טים, ברקודים או תמונות מוצר שהוזנו מראש. במקום זאת, בכל בדיקה היא מבצעת **השוואה ישירה בין שתי התוויות שבאותה תמונה**:

1. מכל תווית מחלצים "זהות מוצר" מנורמלת: `{ בעל_חיים, חלק, מצב }` (למשל אווז / כבד / קפוא).
2. משווים בעיקר את **החלק** (כבד, שוק, כנף, חזה, לב, קורקבן, שומן, ירך) ואת **בעל החיים** ואת **המצב**.
3. התאמה נקבעת רק אם **בעל החיים + החלק + המצב** תואמים. אחרת – חריגה.

**מותר להתעלם מ:** סדר מילים, שפה (עברית/אנגלית/הונגרית), יחיד/רבים, שגיאות OCR קטנות, פיסוק, שם היצרן, הכשר, עיצוב התווית, ומשקל הקרטון – כל עוד זהות המוצר זהה.

**אסור לקבוע התאמה** רק כי מופיעות מילים משותפות כמו "אווז", "קפוא", "כשר" או "12 ק"ג". "כבד אווז קפוא" ו"שוק אווז קפוא" = מוצרים שונים = חריגה.

החלק (part) הוא הנתון הקריטי. המערכת ממפה כל ניסוח לערך קנוני מתוך אוצר מילים מבוקר:

```
כבד     = liver   = máj      = foie
שוק/ירך = leg     = comb      = cuisse
כנף     = wing    = szárny(tő)= aile
חזה     = breast  = mell      = poitrine
לב      = heart   = szív
קורקבן  = gizzard = zúza
שומן    = fat     = zsír
```

## 3. תהליך העבודה של המערכת (Pipeline)

לאחר שהמלקט מעלה תמונות של לקוח אחד:

1. שמירת התמונה/ות המקוריות ללא שינוי (אחסון מאובטח, לא ציבורי).
2. שיפור איכות עותק־עבודה בלבד לצורך קריאה (חדות/ניגודיות) – **בלי לגעת במקור**.
3. זיהוי אזור המדבקה הכחולה ואזור תווית היצרן בכל קרטון (Vision / detection).
4. חיתוך שני האזורים לעיבוד.
5. OCR על כל אזור (טקסט גולמי מלא).
6. ניתוח Vision + LLM: פירוש הטקסט בעברית/אנגלית/הונגרית.
7. חילוץ שם הלקוח (מהמדבקה הכחולה).
8. חילוץ המוצר שהוזמן (מדבקה כחולה) והמוצר שנמצא (תווית קרטון).
9. תרגום טקסטים זרים לעברית.
10. נרמול שני הצדדים למבנה `{ בעל_חיים, חלק, מצב, משקל, מק"ט, ברקוד }`.
11. השוואת המוצרים (בעיקר בעל־חיים + חלק + מצב).
12. חישוב רמת ביטחון 0–100.
13. קביעת סטטוס (תקין / לבדיקת מנהל / חריגה).
14. שמירת כל התוצאות + הטקסט הגולמי + התרגום + הנרמול.
15. שליחת התראת Push למנהל כאשר יש חריגה בוודאות גבוהה.
16. הצגת התוצאה למלקט (הודעה קצרה) ולמנהל (כרטיס מלא).

**טיפול בכמה קרטונים בתמונה אחת:** מזהים כל קרטון בנפרד, ומצמידים לכל תווית יצרן את המדבקה הכחולה הקרובה לה גיאומטרית. יוצרים עד N בדיקות פנימיות (אזור מדבקה כחולה, אזור תווית קרטון, הוזמן, נמצא, תוצאה, ביטחון). **אם לא ניתן לדעת בוודאות איזו מדבקה שייכת לאיזה קרטון – לא מנחשים, מעבירים לחריגות.**

**כמה לקוחות בתמונה אחת:** אם באותה בדיקה מזוהים שני שמות לקוח שונים → עוצרים ומסמנים חריגה: "זוהו מדבקות של יותר מלקוח אחד. יש להעלות כל לקוח בנפרד."

## 4. חישוב רמת ביטחון וספים

לכל זיהוי מחושב ציון 0–100 (משוקלל מ: איכות ה־OCR, ודאות הנרמול, בהירות התמונה, התאמת השדות).

- **90–100:** התאמה בוודאות גבוהה → נשמר כתקין.
- **75–89:** מועבר לבדיקת מנהל.
- **מתחת ל־75:** חריגה אוטומטית.

הספים ניתנים לשינוי על ידי המנהל בהגדרות. גישת המערכת שמרנית: **עדיף להתריע על בדיקה תקינה מאשר לאשר בטעות ליקוט שגוי. באין ודאות – לא מנחשים ולא מסמנים תקין.**

## 5. מבנה המסכים

### 5.1 אזור מלקט (המסך הפשוט ביותר)

- כפתור גדול **"התחל בדיקה חדשה"**.
- פתיחת מצלמת האייפון ישירות; צילום כמה תמונות ברצף לאותו לקוח.
- תצוגה מקדימה; מחיקת תמונה לא טובה וצילום מחדש.
- כפתור גדול **"סיום ושליחה"**; פס התקדמות בהעלאה; הודעת אישור ברורה.
- שמירה זמנית במכשיר (offline) כשהאינטרנט חלש, והעלאה אוטומטית כשהחיבור חוזר.
- מניעת שליחה כפולה.
- רשימת הבדיקות **של המלקט עצמו מהיום בלבד**.
- כל לקוח = בדיקה נפרדת; מעבר ללקוח הבא = בדיקה חדשה.
- שם הלקוח נקרא אוטומטית מהמדבקה הכחולה – **המלקט אינו מקליד דבר**.

תוצאה שמוצגת למלקט לאחר העלאה: "הבדיקה תקינה" / "הבדיקה הועברה לבדיקת מנהל" / "לא ניתן לקרוא את התמונה, יש לצלם מחדש". המלקט **אינו** רואה בדיקות של אחרים, את מסך החריגות המלא או את ההגדרות.

### 5.2 אזור מנהל

רשימת כל הבדיקות (תקינות + חריגות) ככרטיסים. כל כרטיס: תאריך ושעה, שם מלקט, שם לקוח שזוהה, מספר תמונות, המוצרים שזוהו, המוצר במדבקה הכחולה, המוצר בקרטון, תוצאה, רמת ביטחון, סטטוס טיפול. פתיחת כל התמונות בגודל מלא + הגדלה + מעבר בין תמונות. צפייה בטקסט המקורי של ה־OCR, בתרגום ובנרמול, ובנימוק ההתאמה/אי־ההתאמה.

חיפוש וסינון לפי: שם לקוח, שם מלקט, מוצר, תאריך, תקין, חריגה, לא ניתן לקרוא, ממתין לבדיקה, טופל, לא טופל. המנהל יכול לעבור רנדומלית על כל תמונה שהועלתה, גם על בדיקות שסומנו תקין.

פעולות לכל בדיקה: "בדקתי – תקין", "טעות ליקוט מאומתת", "זיהוי שגוי של המערכת", "נדרשת תמונה חדשה", "העבר לטיפול", "סגור בדיקה", + שדה הערת מנהל.

### 5.3 אזור חריגות (המסך החשוב ביותר)

מציג **רק** בדיקות שבהן: אי־התאמת מוצר; חוסר ודאות בזיהוי; לא ניתן לקרוא מדבקה כחולה; לא ניתן לקרוא תווית קרטון; כמה לקוחות בתמונה; כמה קרטונים בלי הצמדה ודאית של מדבקה; ברקוד/מק"ט שאינם תואמים; רצף חבילות לא הגיוני (למשל 1/3 ו־3/3 בלי 2/3); תמונה כפולה; כמה מוצרים בתמונה שאחד מהם אינו תואם; ביטחון מתחת לסף; תמונה מטושטשת/כהה/חתוכה/מוסתרת; לא ניתן לזהות בוודאות את המוצר.

כל חריגה מציגה בבולטות: שם לקוח, שם מלקט, שעת העלאה, מוצר שהוזמן (מדבקה כחולה), מוצר שנמצא (תווית קרטון), הסיבה המדויקת, רמת ביטחון, התמונה המקורית, הגדלת אזור המדבקה הכחולה, הגדלת אזור תווית הקרטון, הטקסט המקורי, התרגום, תוצאת הנרמול, והסבר קצר מדוע נקבעה אי־התאמה.

כפתורים: "אשר טעות ליקוט", "זו אינה טעות", "בקש צילום מחדש", "העבר לטיפול", "סגור חריגה", + שדה הערת מנהל.

סטטוס חריגה: חדשה / נצפתה / בטיפול / אושרה כטעות / בוטלה / נשלחה לצילום מחדש / נסגרה. חריגות חדשות מופיעות ראשונות ובולטות, ועל אייקון המסך מונה חריגות חדשות שטרם טופלו.

### 5.4 דשבורד מנהל

בדיקות שהועלו היום, לקוחות שנבדקו היום, תמונות שנבדקו, בדיקות תקינות, חריגות חדשות, חריגות שאושרו כטעות, תמונות שלא ניתן לקרוא, שיעור טעויות לפי מלקט, שיעור טעויות לפי מוצר, רשימת החריגות האחרונות. ללא גרפים מורכבים בשלב זה – נקי, תעשייתי, מהיר.

## 6. משתמשים והרשאות

**מלקט:** מתחבר עם קוד אישי / טלפון+סיסמה / שם משתמש+סיסמה. פותח בדיקה, מצלם ומעלה, רואה את הבדיקות שלו, מצלם מחדש לפי בקשת מנהל. **אינו** רואה בדיקות של אחרים, אינו רואה את כל החריגות, אינו משנה תוצאות, אינו מוחק בדיקה שנשלחה, אינו משנה שם לקוח/מוצר שזוהה.

**מנהל:** רואה את כל הבדיקות והחריגות, מאשר/מבטל חריגות, מתקן זיהוי, מוסיף הערות, מוסיף/משבית/מנהל משתמשים, משנה ספי ביטחון, רואה דוחות, מייצא ל־Excel, צופה בהיסטוריית שינויים, מגדיר מי מקבל התראות.

## 7. מבנה בסיס הנתונים (PostgreSQL / Supabase)

```
users               (id, name, username, phone, password_hash, role[picker|manager],
                     active, created_at)

checks              (id, picker_id→users, customer_name, images_count,
                     overall_result[ok|review|exception|unreadable],
                     status[new|seen|in_progress|confirmed_error|dismissed|
                            reshoot|closed],
                     confidence, created_at, updated_at, closed_at, closed_by)

images              (id, check_id→checks, storage_path, sha256_hash,
                     seq_index, width, height, created_at)      -- מקור בלתי ניתן למחיקה

carton_analyses     (id, check_id→checks, image_id→images,
                     blue_ocr_raw, carton_ocr_raw,
                     blue_translation, carton_translation,
                     blue_normalized  jsonb {animal, part, state, weight, sku, barcode},
                     carton_normalized jsonb {animal, part, state, weight, sku, barcode},
                     detected_customer, package_seq, 
                     match_result[match|mismatch|uncertain],
                     confidence, mismatch_reason,
                     ai_original_result jsonb,        -- תוצאת המערכת המקורית, לעולם לא נדרסת
                     created_at)

exceptions          (id, check_id→checks, carton_analysis_id→carton_analyses,
                     reason_code, status, opened_at, handled_at, closed_at,
                     handled_by→users)

product_dictionary  (id, key jsonb {animal, part, state}, canonical_name_he,
                     aliases jsonb[], sample_texts jsonb[],
                     confirmed_by→users, confirmed_at, created_at)

manager_actions     (id, check_id, exception_id, user_id→users, action_type,
                     manager_correct_value jsonb, note, created_at)

audit_log           (id, entity, entity_id, action, old_value jsonb, new_value jsonb,
                     user_id→users, created_at)

settings            (id, threshold_ok, threshold_review, notify_user_ids jsonb[], ...)

push_subscriptions  (id, user_id→users, endpoint, p256dh, auth, created_at)
```

**עקרונות שמירה:** אסור למחוק או להחליף תמונה מקורית לאחר העלאה. `ai_original_result` נשמר לצד תיקון המנהל – שניהם קיימים במקביל תמיד. כל שינוי נרשם ב־`audit_log`. גישה לתמונות רק דרך קישורים מאובטחים וקצרי־תוקף (signed URLs), למשתמשים מורשים בלבד.

## 8. עיבוד תמונה וזיהוי – המלצת OCR ו־Vision

**ההמלצה: מודל Vision־LLM רב־לשוני כמנוע ראשי, בגיבוי OCR ייעודי לתוויות קשות.**

למה לא OCR "טהור" בלבד: OCR קורא טקסט אך **לא מבין משמעות** – הוא לא יודע ש־`LIBACOMB` = שוק, לא מתרגם הונגרית, ולא קובע שזהות המוצר שונה למרות מילים משותפות. הדרישות כאן (עברית+אנגלית+הונגרית, תרגום, נרמול סמנטי, פלט JSON מובנה, רמת ביטחון) הן משימת **הבנה**, ולכן הליבה חייבת להיות מודל Vision־LLM.

למה לא Vision־LLM לבד: על טקסט זעיר/מטושטש מודל יכול "להשלים" שגוי. לכן על תוויות קשות מריצים גם OCR ייעודי, ומזינים למודל גם את התמונה וגם את הטקסט הגולמי – שילוב שנותן דיוק וגם עמידות.

**ארכיטקטורה מומלצת:**

1. **מנוע ראשי (מומלץ ל־MVP): OpenAI Vision (GPT‑4o / דומה)** – מקבל את חיתוך התמונה + הנחיה לפלט JSON מובנה עם השדות הנדרשים. מצטיין בעברית + הונגרית + חילוץ מובנה + נימוק. קל לאינטגרציה.
2. **גיבוי OCR לתוויות קשות: Google Cloud Vision או Azure Document Intelligence** – מריצים כשהביטחון של המנוע הראשי נמוך, ומזינים את הטקסט חזרה למודל לנרמול.
3. **שכבת הפשטה (Provider abstraction):** ממשק `VisionProvider` אחיד, כך שניתן להחליף ספק AI בעתיד או לחבר את המערכת ל־Priority דרך API בלי לשכתב את הלוגיקה.

**כל קריאות ה־OCR/AI מתבצעות בשרת בלבד**, עם מפתחות במשתני סביבה – אף מפתח לא נשמר בדפדפן.

**מכל תווית מנסים לחלץ:** שם לקוח (במדבקה הכחולה), בעל חיים, חלק/מוצר מרכזי, מצב (קפוא/מצונן), משקל אריזה, מק"ט/ברקוד (כשקריא), שם יצרן, שפת התווית, תרגום לעברית (בתווית זרה), ורמת ביטחון.

הערת מיקום נתונים: ספקי ה־Vision הגדולים (OpenAI/Google/Azure) הם ענן אמריקאי/עולמי. אם נדרשת שמירת נתונים **בישראל בלבד**, זה משפיע על בחירת הספק ועל אזור ה־Supabase – ראה שאלות בסעיף 11.

## 9. מילון מוצרים אוטומטי (למידה הדרגתית)

המערכת בונה מילון פנימי לאורך זמן, בלי שתזין מראש את עשרת המוצרים:

1. מוצר חדש מזוהה ב־Vision + OCR + תרגום.
2. נשמרים הטקסט המקורי והשם המנורמל.
3. אם אין ודאות מספקת → הבדיקה עוברת לבדיקת מנהל.
4. כשהמנהל מאשר את הזיהוי → המוצר נוסף ל־`product_dictionary` (מפתח מנורמל + כינויים + דוגמאות טקסט).
5. בפעמים הבאות המערכת משתמשת במה שכבר אושר כדי לשפר דיוק וביטחון.

כשהמנהל מסמן "זיהוי שגוי של המערכת" נשמרים: מה המערכת זיהתה, מה המנהל קבע כנכון, התמונה המקורית, אזור המדבקה הכחולה, אזור תווית הקרטון, הטקסט המקורי, התרגום, שם המוצר הנכון, שם הלקוח, התאריך, ושם המלקט – והמערכת משתפרת מהעבודה האמיתית.

## 10. התראות Push לאייפון

בזיהוי אי־התאמה/חריגה בוודאות גבוהה נשלחת מיד **Web Push** למנהל. נוסח לדוגמה:

> חריגת ליקוט חדשה. לקוח: קיבוץ אילות. הוזמן: כבד אווז קפוא. זוהה בקרטון: שוק אווז קפוא.

לחיצה על ההתראה פותחת ישירות את החריגה. באייפון, Web Push דורש התקנת ה־PWA למסך הבית ואישור הרשאה – לכן ייבנה מסך הסבר קצר להתקנה ולאישור התראות. בפיתוח מקומי שבו אי אפשר לשלוח Push אמיתי, תוצג התראה פנימית ברורה בתוך המערכת, והתשתית תיבנה כך שניתן להפעיל Web Push אמיתי בפריסה.

## 11. טכנולוגיה ואבטחה

**Stack:** Next.js + React + TypeScript + Tailwind CSS (PWA – Service Worker + Web App Manifest). **Backend/DB/Auth/Storage:** Supabase (PostgreSQL). **AI:** שכבת `VisionProvider` מעל OpenAI Vision (ברירת מחדל) עם גיבוי Google/Azure OCR. מערכת אמיתית עם Frontend + Backend ובסיס נתונים אמיתי – לא קובץ HTML עם Local Storage.

**אבטחה:** כל משתמש מתחבר; הפרדת הרשאות מלקט/מנהל (Row Level Security); מלקט רואה רק את שלו; מנהל רואה הכול; מפתחות רק במשתני סביבה בשרת; כל קריאת OCR/AI דרך השרת; תיעוד פעולות ושינויים; השבתת משתמש; גיבוי DB; קישורי תמונה מאובטחים קצרי־תוקף.
